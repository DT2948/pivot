# Architecture

Pivot has a simple batch pipeline.

Fetchers load jobs from public sources. `GreenhouseFetcher` supports Anthropic through the public board API. `NvidiaWorkdayFetcher` uses NVIDIA's official Workday CXS careers API. `GoogleCareersFetcher` parses official Google Careers result/detail pages. `MicrosoftCareersFetcher` uses Microsoft's official `apply.careers.microsoft.com` search and position-detail API. `MetaCareersFetcher` attempts Meta's official Careers GraphQL operation with normal public HTTP only and reports `failed` with `Meta public careers endpoint returned 400` if Meta blocks anonymous requests. `TeslaCareersFetcher` uses Tesla's official careers API and reports `failed` if Tesla blocks the runner with a 403. `GitHubMarkdownAdapter` reads raw Markdown from curated public repos. Apple is paused for now and is not fetched by default.

Every source becomes a normalized `Job` model. This gives filtering, scoring, email, and state code one common shape.

Filtering is deterministic and cheap. It classifies role family, checks role keywords, seniority, undergraduate degree fit, years of experience, location, internships, citizenship, clearance, and sponsorship language before Gemini is considered. Location detection recognizes U.S. state abbreviations, common city aliases such as SF/NYC/LA/DC/Bay Area, and mixed U.S./non-U.S. location strings when at least one location is clearly U.S.

Alert ordering prioritizes Google direct roles first, Google curated roles second, other direct target-company roles next, other target-company curated roles next, and non-target curated matches last. Alert gating is conservative. Target-company roles without a clear new-grad or early-career signal require Gemini review before emailing. Curated repo roles can rule-alert when they have a strong new-grad signal, pass hard filters, and meet the curated rule-only threshold. Fellowship/program, sales, legal, finance, product-management, support, hard no-sponsorship, citizenship, and clearance roles cannot alert by default for curated/unverified sources. Direct target-company roles keep sponsorship, citizenship, and clearance text as debug context instead of alert blockers.

Gemini scoring is optional. Only candidates above the configured rule-score floor are sent, and only up to `gemini.max_jobs_per_run` attempted calls. Scores are validated on a 0-10 scale; percent-style scores such as 40 are normalized to 4.0. Missing keys, invalid scores, quota errors, 503 bursts, and API failures fall back safely to rules. Required-Gemini candidates that fall back do not alert.

Email uses SMTP. Strong new matches are sent after scoring in a multipart HTML/plain-text digest grouped into Google Priority, Target Companies, and Other Strong Matches. The subject line follows the highest-priority new alerts in the run: Google-priority first, then other target-company alerts, then strong non-target matches. Test email mode skips fetching and state updates.

State lives in `data/seen_jobs.json`. Discovery history (`first_seen_at`, `last_seen_at`, last score and description hash) is separate from successful delivery (`alerted_at`, `alerted_snapshot`). An unchanged never-alerted job with explicit `alerted_at: null` can qualify later. Delivered jobs do not re-email when scores, code or prompts change. Meaningful posting changes compare against the last delivered snapshot, so an intermediate below-threshold observation cannot consume a later changed-job alert. SMTP failure still aborts without saving delivery state; successful delivery updates only emailed keys. Dry runs never write state.

The prior implementation recorded every scored candidate but suppressed every unchanged seen key, including never-delivered jobs. This was a real bug. Migration preserves all tracked history: existing delivery timestamps remain authoritative, explicit nulls remain eligible, and legacy records lacking delivery metadata are conservatively treated as previously delivered (`legacy_delivery_unknown`) to avoid a historical re-email. No state reset is needed.

GitHub Actions runs lint, tests, and Pivot. It uploads last-run debug JSON files as workflow artifacts and commits only `data/seen_jobs.json` back to the repo when the seen state changes. `data/last_run_alerts.json` records every alert-worthy candidate with its priority group, score, source, seen status, emailed status, and skip reason.


## Review allocation and assessment reuse

Fetch, deduplicate, filter, score, Gemini review, alert eligibility, prioritize, delivery deduplication, email, then persist. Deterministic rejection always precedes Gemini. Required reviews precede optional reviews. Within each class: Google, all other active targets equally, then non-targets; descending rule fit precedes source priority. Google is first because of an actively advocating mentor. Oracle, Intel and AMD have contacts, with no invented difference in referral strength. Apple remains paused.

Clearly rejected jobs and blocked role families consume no attempts. Duplicate postings are removed before scoring. Unchanged delivered jobs consume no calls. A complete typed Gemini assessment is cached in the existing state file with a hash of model, profile, settings, normalized prompt/scoring source code, and normalized job content (excluding raw ATS metadata and timestamps). A matching assessment is reused, with current rule gates and thresholds applied again. Changed scoring context invalidates reuse without resetting delivery history. The code fingerprint covers `gemini_scorer.py` (including the actual prompt), `filtering.py`, `scoring.py`, `verification.py` and `targets.py`; line endings are normalized so Windows and GitHub Actions agree. No manual prompt-version bump is needed for these edits. Rule-only / failed assessments are not cached as Gemini results. No separate database or queue is used. The default remains two attempted calls including failures/retries; quota and unavailable fallback behavior is preserved.

## New direct company sources

- Oracle/OCI: `https://eeho.fa.us2.oraclecloud.com/hcmRestApi/resources/latest/recruitingCEJobRequisitions`, expanding `requisitionList`, plus `recruitingCEJobRequisitionDetails`. Host and site `CX_45001` are published by `https://careers.oracle.com/en/sites/jobsearch/jobs`. Four keyword searches, at most 25 results each, deduplicated by requisition ID; at most 20 detail requests, US first. Details retain description, qualifications, responsibilities and secondary locations. Numbered Oracle Developer 3-6 / IC3-6 roles are rejected as beyond early career.
- Intel: `https://intel.wd1.myworkdayjobs.com/wday/cxs/intel/External/jobs` plus public job detail paths. Four searches, at most 20 results each; at most 20 detail requests, US paths first while retaining multilocation detail resolution. Descriptions and additional locations are preserved.
- AMD: `https://careers.amd.com/api/jobs`, four US-focused keyword searches, at most 20 results per search. Descriptions come directly from `jobs[].data`; stable official job pages link to applications. Requisition IDs deduplicate searches.

Searches are intentionally bounded, without exhaustive pagination. Oracle/Intel skip plainly senior and unrelated titles before detail allocation. All adapters use ordinary unauthenticated HTTP with 20-second timeouts. They validate expected response structures and descriptions: HTML challenges, malformed records/JSON, missing descriptions, HTTP errors and timeouts report failed source health rather than false success. Valid empty search lists are successful empty searches. A detail failure currently fails that source's batch rather than claiming complete coverage. Other sources continue; curated coverage is independent and only available for jobs those repositories list.

Live read-only verification on October 19, 2026 extracted 6 Oracle postings (all 6 descriptions), 10 Intel (all 10), and 68 AMD (all 68). Example application pages: Oracle 346357 (Undergrad OCI), Intel JR0287686 (Software Engineer - Datacenter), AMD 86642 (a senior listing correctly rejected by filtering). This verifies extraction, not eligibility of every result. The new endpoints were accessible; Meta/Tesla can still be blocked as described above. The local environment's configured proxy refused connections, so live verification used direct public HTTP without a proxy.

## Fit policy

The refined profile distinguishes education, skills, demonstrated research/project/THON experience and career interests. Backend/systems/infrastructure and ML systems are equally important; general new-grad SWE requires no ML keywords. Implementation-focused research engineering, substantial backend full-stack, and forward deployed work receive individual assessment. Graph ML is not a mandatory specialization. Bare AI mentions earn no deterministic bonus. Execution synonyms share one scoring group; compiler/runtime and infrastructure synonyms are grouped to avoid repetitive counting. Existing thresholds remain unchanged. Explicit advanced-degree-only, seniority, hardware-only, experience and geographic exclusions apply regardless of employer. An early-career title no longer overrides explicit excessive experience requirements.

Gemini previously preferred a short backend/AI keyword list and unconditionally instructed sponsorship/citizenship penalties, conflicting with direct-target policy. It now assesses responsibilities and bachelor's eligibility, calibrates 9-10 exceptional / 8 strong / 7 good / 5-6 partial / below 5 weak, separates company priority from technical fit and receives a per-job sponsorship policy. Direct active targets (including Oracle, Intel and AMD) preserve restriction text as concerns without being penalized solely for those restrictions. Curated/non-target restrictions remain enforced. This visibility preference is not a sponsorship or eligibility claim.
